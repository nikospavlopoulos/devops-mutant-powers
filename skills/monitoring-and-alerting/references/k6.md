# k6 Load Tests

Load this when writing, reviewing or reading a k6 load test. A load test is a **live change**: it sends real traffic
that can degrade or take down the target and everything it shares (databases, gateways, rate limits, other
tenants). Never run one — not even a one-user smoke run — against production or a shared system without explicit
approval from its owner; name the target explicitly, tell the owners when it runs, and start with a smoke test. A
test passes or fails only through **thresholds**; checks alone never fail a run.

## 1. Safety gate (before every run)

- **Target named, no default.** Pass the base URL with `-e BASE_URL=…` and read it from `__ENV`; the script refuses
  to start without it, so nothing runs against a hard-coded or forgotten URL.
- **Environment:** larger tests belong in pre-production; k6's own guidance allows production only with minimal
  load (smoke-style checks) and without affecting real users — still with the owner's approval.
- **Smoke first:** 1 virtual user (VU) for a short time to prove the script and the target, then raise load step by step.
- **Stop plan:** who watches, which signal aborts (`abortOnFail` thresholds, or stop the run), who to call.

```bash
# (approval when the target is shared) — the target is explicit on every run
k6 run -e BASE_URL=https://staging.example.com script.js
```

## 2. Test types

| Type | Purpose |
|---|---|
| Smoke | Script works and the system copes with minimal load — always first |
| Average-load | Behaviour under expected normal traffic |
| Stress | Behaviour above the expected average |
| Soak | Reliability over a long period (leaks, slow degradation) |
| Spike | Sudden, short, very large surges |
| Breakpoint | Raise load gradually to find the capacity limit |

## 3. Thresholds are the pass/fail gate

```javascript
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL;
if (!BASE_URL) throw new Error('set -e BASE_URL=<non-production URL>');   // aborts before any request

export const options = {
  scenarios: {
    smoke: { executor: 'constant-vus', vus: 1, duration: '30s' },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],                         // under 1% failed requests
    'http_req_duration{name:get-item}': ['p(95)<300'],      // per-endpoint latency, via the name tag
    checks: ['rate>0.99'],                                  // makes checks count
  },
};

export default function () {
  const id = Math.ceil(Math.random() * 100);
  const res = http.get(`${BASE_URL}/items/${id}`, { tags: { name: 'get-item' } });
  check(res, { 'status is 200': (r) => r.status === 200 });
}
```

- A failed threshold ends the run with exit code **99** (`ThresholdsHaveFailed`) — that is what fails continuous
  integration (CI). A script that throws (like the missing `BASE_URL` above) also exits non-zero, before any request.
- Checks record pass/fail rates but never change the exit status — gate them with a `checks` threshold.
- All expressions for one metric go in **one** array: repeating the same key in `thresholds` silently ignores the
  others.
- Thresholds on tagged sub-metrics: `'metric{tag:value}'`. Confirm in the end-of-test summary that each sub-metric
  actually received samples before trusting its result.
- `abortOnFail: true` stops the run when a threshold is crossed; add `delayAbortEval` so it does not abort on the
  first noisy seconds.

## 4. Scenarios and executors: open vs closed model

- Scenario options: `executor` (required), `startTime`, `gracefulStop` (default 30s), `exec`, `env`, `tags`.
- **Closed model** — the VU-driven and iteration-driven executors (`constant-vus`, `ramping-vus`, `shared-iterations`,
  `per-vu-iterations`): the next iteration starts only when the previous one ends, so when the target slows down
  the arrival rate drops with it (coordinated omission) and the test hides the slowdown.
- **Open model** — `constant-arrival-rate`, `ramping-arrival-rate`: iterations start at the configured rate
  regardless of response time. Use it for capacity, breakpoint and service-level-objective (SLO) tests. Options:
  `rate`, `timeUnit` (default 1s), `duration`, `preAllocatedVUs`, `maxVUs`. Do not end the iteration with `sleep()`
  — the executor already paces it.
- **`dropped_iterations` > 0** means iterations that never started: too few VUs early in the run, or the target
  slowing later. The intended rate was not delivered — explain it, or set a threshold on it, before using the result.

```javascript
scenarios: {
  orders: {
    executor: 'constant-arrival-rate',
    rate: 50, timeUnit: '1s', duration: '10m',     // CHANGE: 50 iterations/s for 10 minutes
    preAllocatedVUs: 50, maxVUs: 200,
  },
},
```

## 5. Metrics that are easy to misread

- `http_req_duration` = sending + waiting + receiving; it **excludes** DNS lookup and connection set-up.
- `http_req_failed` is the rate of responses outside the expected statuses — by default **200–399**. A 200 with an
  error in the body counts as success: add a `check` on the body. For an endpoint that is designed to return 404 or
  409, pass a per-request `responseCallback: http.expectedStatuses(...)` instead of loosening the global
  `http_req_failed` threshold.
- Dynamic URLs create one tag value per URL: group them with `tags: { name: '…' }` or the `http.url` template
  literal.
- `http_reqs`, `iterations`, `vus` show what load was really applied — compare with what you intended.

## 6. Reading results

- Per-endpoint thresholds: a global p95 can stay green while one route is slow.
- Watch the **load generator**: keep its CPU under about 80% and memory under 90%; a saturated generator reports
  response times far higher than the real ones. Set `discardResponseBodies: true` unless the script reads bodies.
- Correlate with server-side metrics, traces and logs for the same window before blaming or clearing the backend.

## 7. Common mistakes

| Mistake | Fix |
|---|---|
| No thresholds, or only checks | Thresholds on `http_req_failed`, latency per endpoint, and `checks` |
| Closed-model executor for a capacity or SLO test | `constant-arrival-rate` / `ramping-arrival-rate` |
| `dropped_iterations` ignored | Raise VUs or explain the slowdown; threshold it |
| Running against production, a shared system or an unnamed default URL | `-e BASE_URL`, no default, owner's approval |
| Loosening `http_req_failed` globally for one expected 4xx | Per-request `responseCallback` |
| `sleep()` at the end of arrival-rate iterations | Remove it; the executor paces iterations |
