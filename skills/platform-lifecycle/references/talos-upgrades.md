# Talos Upgrades — OS and Kubernetes

Load this file to plan or review a Talos Linux OS upgrade (`talosctl upgrade`) or a Kubernetes upgrade on Talos
(`talosctl upgrade-k8s`): which comes first, the version path, the installer image, the per-node loop with health
checks, flags that changed between releases, and what to do when an upgrade fails. Verified 2026-10-11 against the
Talos v1.14 documentation; behaviour that differs between releases names the release. Every command marked
**[APPROVAL]** changes live state and needs the owner's explicit go; everything else is read-only.

**Target flags.** `-e/--endpoints` is the API endpoint the client talks to (point it at the control-plane nodes or
their load balancer; several endpoints give automatic fail-over); `-n/--nodes` is the node the call acts on, as the
endpoint sees it. Always pass `-n` explicitly rather than keeping nodes in `talosconfig`. Keep more than one endpoint
while a control-plane node reboots, so the client can fail over.

## 1. Two upgrades, two commands

| What | Command | Scope |
|---|---|---|
| Talos OS (kernel, OS image, system extensions) | `talosctl upgrade` | one call per node |
| Kubernetes (control-plane components, kube-proxy, kubelet, bootstrap manifests) | `talosctl upgrade-k8s` | sent to one control-plane node, upgrades the whole cluster |

Since Talos v1.0 an OS upgrade does not upgrade Kubernetes. The support matrix decides which upgrade goes first:

| Talos | Kubernetes versions supported |
|---|---|
| 1.14 | 1.33, 1.34, 1.35, 1.36, 1.37 |
| 1.13 | 1.31, 1.32, 1.33, 1.34, 1.35, 1.36 |

- Cluster on Kubernetes 1.31 or 1.32 → bring Kubernetes to at least 1.33 on Talos 1.13 **before** moving to Talos 1.14.
- Kubernetes 1.37 → Talos 1.14 **first**.

## 2. Version and path rules

- **Talos path:** config migration is tested only between adjacent minor releases, so go through the latest patch of
  every intermediate minor (e.g. 1.12.x → latest 1.12 → latest 1.13 → 1.14.x). Never jump minors.
- **`talosctl` version:** the docs recommend the version that matches the cluster's running Talos version. The
  `--image` default is the installer of the `talosctl` version in use — pass `--image` explicitly every time.
- **Kubernetes skew (upstream policy):** in highly available (HA) clusters, `kube-apiserver` instances stay within
  one minor of each other; `kube-apiserver` must not skip a minor when upgrading; kubelet never newer than
  `kube-apiserver` and at most three minors older. So Kubernetes goes one minor per `upgrade-k8s` run, control plane
  before kubelets — the order `upgrade-k8s` follows (§6).

## 3. Read the target's upgrade notes first (v1.14 examples)

- **Installer image moved.** From v1.14 `ghcr.io/siderolabs/installer` is no longer published. Installer images
  come from the Image Factory: `factory.talos.dev/<platform>-installer/<schematic-id>:<version>` (the docs show
  `metal-installer` and `aws-installer`; copy the exact reference for your platform from the factory UI).
- **Use the node's own schematic.** The schematic ID is content-addressed and lists the node's system extensions;
  `talosctl get extensions` shows it as the extension named `schematic`. Upgrading with another schematic (the
  vanilla one, `376567988ad3…b4ba`, has none) replaces the node's set of extensions. Installer images carry system
  extensions only — kernel arguments and META in the schematic are ignored.
- **Multipath:** an `ExtensionServiceConfig` named `multipathd` must be migrated to an `EtcFileConfig` for
  `multipath.conf` *before* the upgrade, or `multipathd` waits forever afterwards.
- **etcd:** v1.14 runs etcd 3.6 or later only, and moves etcd's HTTP endpoints (`/metrics`, `/health`) from port
  2379 to 2383 — update scrape targets and firewall rules (2379 keeps serving gRPC).
- **New defaults are not applied on upgrade:** workload isolation (`SecurityProfileConfig`) and periodic filesystem
  trim (`FilesystemTrimConfig`) are enabled only in configs generated by v1.14; upgraded clusters opt in by adding
  the documents.
- **Deprecated `v1alpha1` fields** still work in v1.14; setting a deprecated field and its replacement document
  together is rejected for most of them (`references/talos-machine-config.md` §2).

## 4. Pre-flight (read-only, before every node)

```bash
# Versions: client vs every node; kubelet versions as Kubernetes sees them
talosctl --context <talos-ctx> version --client
talosctl --context <talos-ctx> -n <cp-1-ip>,<cp-2-ip>,<cp-3-ip>,<worker-1-ip> version --short
kubectl --context <ctx> get nodes -o wide
# Schematic (system extensions) per node — the installer image must carry the same ID
talosctl --context <talos-ctx> -n <node-ip> get extensions
# etcd: every member listed, one leader, empty ERRORS column, no alarms
talosctl --context <talos-ctx> -n <cp-1-ip>,<cp-2-ip>,<cp-3-ip> etcd status
talosctl --context <talos-ctx> -n <cp-1-ip> etcd members
talosctl --context <talos-ctx> -n <cp-1-ip>,<cp-2-ip>,<cp-3-ip> etcd alarm list
# Whole-cluster health from one control-plane node
talosctl --context <talos-ctx> -n <cp-1-ip> health \
  --control-plane-nodes <cp-1-ip>,<cp-2-ip>,<cp-3-ip> --worker-nodes <worker-1-ip>,<worker-2-ip>
```

Also: PodDisruptionBudgets (PDBs) that allow zero disruptions and storage replicas on the node (`references/commands.md`
§1, `references/decommission.md` §1). How `talosctl upgrade` behaves when a PDB never allows eviction within
`--drain-timeout` is not documented — clear blocking PDBs first instead of relying on the timeout.

## 5. Order and the per-node loop

1. **etcd snapshot first**, stored encrypted off the node (`references/talos-etcd-recovery.md` §2) **[APPROVAL]**.
2. **Control-plane nodes one at a time**, health between each; then **workers one at a time** (or small batches that
   stay within PDB and storage-replica limits). The docs use the same procedure for both roles and do not mandate
   control plane before workers for the OS — treat that order as convention. What they do state: Talos refuses a
   control-plane upgrade that would lose etcd quorum and lets only one control-plane node upgrade at a time, yet
   upgrading every node at once is still not recommended, because other quorum-based software (for example Rook/Ceph)
   may not survive several nodes rebooting together.
3. **Per node:**

```bash
# [APPROVAL] one node, explicit installer image with the node's own schematic
talosctl --context <talos-ctx> -e <cp-2-ip>,<cp-3-ip> -n <cp-1-ip> upgrade \
  --image factory.talos.dev/metal-installer/<schematic-id>:<target-version> --wait
# Watch it (read-only): kernel log on the node
talosctl --context <talos-ctx> -n <cp-1-ip> dmesg -f
# After: new version, same schematic, node Ready and schedulable, etcd and cluster health as in §4
talosctl --context <talos-ctx> -n <cp-1-ip> version --short
talosctl --context <talos-ctx> -n <cp-1-ip> get extensions
```

**What happens (v1.13+):** `talosctl upgrade` uses the `LifecycleService` API. The install step (new boot assets)
runs while the node still runs its workloads; then the node is cordoned and drained, rebooted (kexec unless
`--reboot-mode powercycle`) and uncordoned. Flags in the v1.14 CLI: `--drain` (default true), `--drain-timeout`
(default 5m), `--wait` (default true), `--debug` (implies `--wait`, shows kernel logs), `--timeout` (default 30m),
`--reboot-mode default|force|powercycle`, `--no-reboot` (install now, skip the reboot and the drain — the node keeps
running the old version until it is rebooted; that reboot is a separate **[APPROVAL]** step, drained first with
`talosctl reboot --drain` or `kubectl drain`), `--legacy` (force the legacy API).

**Old runbooks:** `--stage`, `--preserve`, `--force` and `--insecure` belong to the legacy `MachineService.Upgrade`
API; v1.13 deprecated them (removal planned for 1.18) and the v1.14 CLI reference no longer lists them. `--preserve`
has been implied since v1.8 — the system disk is never wiped during an upgrade. The legacy `--force` skipped the etcd
health and member checks and could lose data; never revive it. v1.13 documents one reason for `--legacy`: the new API
does not pass `.machine.install.extraKernelArgs` to GRUB nodes with `grubUseUKICmdline: false` (the upgrade reports
success, the kernel command line silently changes); `--legacy` is a stopgap until 1.18, moving the arguments into the
unified kernel image (UKI) is the lasting fix. Check whether your target release still lists this limitation.

## 6. Kubernetes: `talosctl upgrade-k8s`

```bash
# Read-only plan: deprecated APIs still in use, discovered nodes, each component's from → to
talosctl --context <talos-ctx> -n <cp-1-ip> upgrade-k8s --to <k8s-version> --dry-run
# [APPROVAL] the real run — one control-plane node addressed, every node upgraded
talosctl --context <talos-ctx> -n <cp-1-ip> upgrade-k8s --to <k8s-version>
```

- **Phases:** pre-pull images on the nodes → patch each control-plane node's machine config with the new component
  images (static pods follow) → update the `kube-proxy` DaemonSet → update the kubelet on every node and wait for
  it → re-apply bootstrap manifests → prune resources no longer needed (v1.13+; `--manifests-no-prune` turns it off).
  Kubelet updates may restart workloads.
- **Failure:** the command can be re-run and continues from where it failed.
- **Bootstrap manifests (v1.13+):** applied with server-side apply, and Talos forces ownership of every field it sets,
  so in-cluster edits to CoreDNS, kube-proxy or inline/extra manifests are overwritten. Removing a manifest from the
  machine config marks its objects for pruning — `--dry-run` shows them first.
- **Custom component images:** pass the `--*-image` flags (e.g. `--apiserver-image`), or the defaults are used.
- **After the run** the live machine configs carry the new component versions; a full `controlplane.yaml` or
  `worker.yaml` kept in Git is now stale and re-applying it downgrades components. Update the
  `--kubernetes-version` input and regenerate (`references/talos-machine-config.md` §3).
- Clusters managed by Omni are upgraded from Omni, not with `talosctl upgrade-k8s`.

## 7. When it fails — rollback

| Situation | What Talos does / what you do |
|---|---|
| Installer image reference invalid or unreachable | download fails, the upgrade aborts; node unchanged |
| Filesystems cannot be unmounted cleanly | the upgrade aborts and the node reboots |
| New image fails to boot | A/B scheme: the bootloader falls back to the previous kernel and OS image |
| Talos healthy, workloads broken on the new version | `talosctl --context <talos-ctx> -n <node-ip> rollback` **[APPROVAL]** — sets the previous image as boot target and reboots; only the previous image is kept |
| `upgrade-k8s` stopped halfway | fix the cause, re-run the same command |

Before the Kubernetes step, hold a fresh etcd snapshot: it is the last-resort recovery point
(`references/talos-etcd-recovery.md` §6).

## 8. Rehearse

Run the exact path (same versions, same schematic, same flags) on a staging cluster first. Talos in Docker is meant
for continuous integration (CI) and local testing and cannot rehearse this: `upgrade`, `reset` and similar APIs do
not apply in container mode.
